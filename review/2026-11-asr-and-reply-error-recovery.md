# ASR 分 P 校验与评论提交失败复盘

记录日期：2026-11-12。当前交付状态：代码已修改并完成 bundle；真实账号上的重试结果尚未验证。

## 1. 问题背景

通知处理遇到两类连续故障。视频上下文获取时，ASR worker 返回 `ASR worker failed: ValueError.`，导致回复被跳过；修复 ASR 后，回复生成成功，但向 B 站提交评论时接口返回 `12022`，该异常继续冒泡为整个 notification polling failed。

目标是接受 yt-dlp 对分 P 视频的合法标识，并让单条评论提交失败不终止本轮其他通知。已删除或不存在的目标评论应结束对应待办；可能恢复的提交错误应保留待重试。

## 2. 方案决策

- yt-dlp 返回的 `id` 除裸 BVID 外，也允许精确匹配 `{BVID}_p{page}`。仍按请求页码校验，避免把其他分 P 的音频误认为目标视频。
- ASR worker 错误输出保留异常文本，避免只看到异常类名、无法区分输入校验与第三方库错误。
- 评论 API 错误封装响应 code，并附带 B 站返回的 `message`。
- `12006`（没有该评论）和 `12022`（已删除）视为不可恢复的目标失效：记录后将通知标记完成，避免每轮重复生成和提交。其他提交错误保留待办，记录后继续处理本轮剩余通知。
- 不对失败评论自动改写或再次发布；服务端仍是是否接受评论的最终判断。

## 3. 实际动作与责任边界

- 助手修改 `asr-worker.py`、`src/lib/bilibili-api.ts`、`src/lib/notifications.ts`、`src/index.ts`，并重建本地 bundle。
- 助手没有通过 B 站账号手动发布评论，也没有修改登录凭据或通知状态文件。

## 6. 效果证据

- 本地 yt-dlp 查询对分 P 1 返回了带 `_p1` 后缀的合法视频 ID；旧实现只接受裸 BVID，因此会在下载阶段主动抛出 `ValueError`。该结果直接验证了 ASR 根因。
- 通知日志记录了 worker 的 `ValueError`，并在视频音频缓存落盘前失败；错误处理此前丢弃了异常文本。
- 评论日志显示 `/x/v2/reply/add` 的 HTTP 状态为 200，之后应用层响应 code 为 `12022`。旧代码只报告 code 并重新抛出，因此轮询任务结束。
- `npm run bundle` 成功完成 Host/Client TypeScript 编译和 tsdown 打包。
- 未运行测试；未在插件重新加载后的真实账号上确认通知被跳过、其他通知继续处理或正常评论发布。
