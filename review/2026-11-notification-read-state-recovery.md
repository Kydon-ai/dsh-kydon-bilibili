# 通知先被读掉后的恢复

记录日期：2026-11-10。状态：通知列表高水位和待办队列已接入；实际账号上的读后仍可抓取行为仍需运行验证。

## 现象

用户在插件下一次轮询前打开 B 站并读掉 @ 或回复通知时，`/x/msgfeed/unread` 会报告未读数为 0。旧流程只按未读数决定拉取和入队数量，因此通知没有写入本地待办；如果此时进程重启或离线，插件没有可靠的恢复记录。

## 根因

未读数是服务端当前阅读状态的计数，不是可恢复的事件队列。待办文件只能保存插件已经抓取到的通知，不能找回还未入队的消息。实现虽然开始在未读数为 0 时请求列表，但扫描代码又用 `items.slice(0, remaining)` 限制条目数；`remaining` 为 0 时没有检查任何列表项，也没有保存新的列表位置。

## 修复方案

- 插件每次轮询都会读取 @ 和回复列表，不再用未读数为 0 跳过列表扫描。
- `notification-handled.json` 升为版本 3，保留 `pending` 和 `handled`，并为 @、回复列表分别保存最新通知的 `id` 与时间戳。
- 首次扫描或从版本 1/2 状态迁移时，用当前未读数将通知写入待办，并把当前列表头部设为基准位置；之后每次扫描会把基准位置之后的新条目写入待办，即使 B 站未读数已经归零。
- 扫描到旧位置后，插件才保存新的列表位置。每条通知先原子写入待办，成功收到 B 站回复响应后，才从待办移除并把去重键写入已处理列表。
- 旧状态文件仍可读取；旧格式没有列表位置，因此迁移时不能判断基准位置之前已读历史中的哪些通知曾经漏处理。

## 汲取教训

- 不要把未读计数当作持久事件记录；用户或其他客户端可以先改变阅读状态。
- 轮询型消费者需要本地高水位或游标，并在昂贵处理前写入待办。
- 必须先确保扫描到的新条目已经持久化，再提交对应的列表位置；否则崩溃会让游标越过未入队的消息。
- 服务端回复和本地文件不是同一个事务。B 站接受回复后、本地完成状态写入前若进程退出，重启后仍可能重复回复。
- 列表接口只要保留新位置之后的通知，就能让本地游标发现它们；如果 B 站不再返回已读条目，插件无法从未读数为 0 推断缺失内容。首次建立基准前已经读掉的旧通知也无法无歧义恢复。
